## 1. Objetivo y alcance

El futuro portal privado reutilizará la aplicación Angular existente para ofrecer una experiencia de gestión deportiva separada del portal público. La primera implementación privada deberá seguir las convenciones ya presentes:

- componentes Angular `standalone`;
- carga perezosa de áreas y páginas;
- `ChangeDetectionStrategy.OnPush`;
- modelos TypeScript tipados;
- diseño mobile-first y responsive;
- estilos reutilizables con la paleta ADR Cross;
- separación clara entre layout, acceso, autenticación futura, modelos y páginas.

Esta fase **no implementa** autenticación real, login, guards ficticios, tokens, roles o sesiones simulados, almacenamiento de roles en `localStorage`, backend funcional, operaciones de base de datos, reservas, pagos, membresías, asistencia, WOD, CRUD operativos, datos personales ficticios, recursos AWS, User Pools de Cognito, APIs ni despliegues.

El portal público actual permanece intacto. Sus rutas, shell, SEO, robots, foco posterior a navegación, menú móvil y accesibilidad no forman parte del alcance de implementación de NP-003.7A.

## 3. Principios de seguridad y autorización

### 3.1 Frontera de confianza

El frontend es un cliente público. Todo lo que llegue al navegador puede ser inspeccionado o modificado por el usuario. Por ello:

1. Los roles y capacidades del frontend organizan la interfaz y mejoran la experiencia de navegación.
2. La autorización efectiva de cada operación reside en el backend.
3. El backend valida identidad, JWT, audiencia, emisor, vigencia, capacidades y alcance del recurso en cada solicitud.
4. Un guard de Angular solo evita navegación innecesaria o muestra acceso denegado; nunca es una barrera de seguridad.
5. Una respuesta HTTP exitosa del backend es la única confirmación de que una operación fue autorizada y ejecutada.

### 3.2 Mínimo privilegio

Cada rol recibe únicamente las capacidades necesarias para su trabajo. Las capacidades con alcance se expresan como restricciones de recurso: profesor para clases asignadas, alumno para recursos propios, community manager para contenido público aprobado y administrador para operaciones globales autorizadas.

Los nombres de capacidades son un contrato conceptual compartido. El backend es la fuente de verdad y puede rechazar una capacidad aunque el cliente la muestre.

### 3.3 Estados de acceso

| Estado | Significado | Comportamiento previsto |
|---|---|---|
| `unauthenticated` | No hay sesión válida | Redirigir a Cognito mediante Authorization Code + PKCE. |
| `authenticated` | Identidad válida verificada por backend | Cargar el shell privado y las capacidades autorizadas. |
| `denied` | Identidad válida, pero sin capacidad o alcance | Mostrar acceso denegado sin datos internos. |
| `expired` | Sesión o token vencido | Interrumpir la operación y renovar o cerrar sesión según el flujo aprobado. |
| `unavailable` | Portal privado aún no habilitado | Mostrar pantalla informativa, sin datos ni login ficticio. |

## 7. Estrategia futura con Amazon Cognito

### 7.1 Flujo previsto

La integración futura deberá usar:

1. Amazon Cognito User Pool.
2. Authorization Code Flow con PKCE.
3. `state` y `nonce` para mitigar replay y confusión de flujos.
4. `code_verifier` generado por el cliente y no persistido en una ubicación insegura.
5. Redirección de retorno con intercambio de código mediante una biblioteca oficial/aprobada.
6. Validación backend del JWT: firma, emisor, audiencia, expiración, scopes/capacidades y claims requeridos.
7. Obtención backend de una sesión mínima para el frontend, sin confiar en roles enviados como parámetros de ruta.
8. Redirección a `/portal/app` solo después de una sesión válida.
9. Manejo explícito de acceso denegado, sesión expirada, logout y errores de red.

### 7.2 Identidad y permisos separados

Cognito responde quién es el usuario. El backend decide qué puede hacer:

- Cognito: `sub`, autenticación, grupo o claims configurados.
- Backend: validación de JWT, política de capacidades, alcance de recurso y reglas de negocio.
- Frontend: muestra navegación y estados coherentes con la sesión autorizada.

El frontend no debe tratar un grupo de Cognito como autorización suficiente para una operación concreta. Una capacidad puede depender de gimnasio, clase asignada, alumno propio, estado de publicación, ventana horaria, estado de membresía o política aprobada.

### 7.3 Gestión de sesión

La implementación futura deberá definir y probar:

- expiración de access token e ID token;
- renovación o cierre de sesión;
- logout en Cognito y eliminación del estado local;
- comportamiento ante reloj del cliente desincronizado;
- navegación durante renovación;
- concurrencia de solicitudes;
- eliminación de estado sensible al cerrar sesión;
- ausencia de roles o tokens persistentes en `localStorage`.

La ubicación exacta de tokens y el mecanismo de renovación se decidirán con la biblioteca de autenticación aprobada y la revisión de seguridad; esta fase no la implementa.

### 7.4 CORS, CSRF y red

- Permitir solo orígenes verificados.
- No usar comodines para solicitudes credenciales.
- Revisar cookies `Secure`, `HttpOnly`, `SameSite` si se adopta sesión por cookie.
- Validar `Origin`/`Referer` cuando corresponda.
- Mantener secretos fuera del repositorio.
- No exponer credenciales de Cognito ni claves privadas en el cliente.

## 10. Riesgos de seguridad y mitigaciones

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Guard ficticio o rol en `localStorage` | Acceso aparente a datos privados | No implementar; backend valida JWT y capacidades en cada operación. |
| Ruta privada registrada sin autenticación | Exposición de dashboards | Mantener rutas privadas fuera de `app.routes.ts` hasta integrar Cognito. |
| XSS en contenido o plantillas | Robo de sesión o manipulación | Sanitización, CSP futura, revisión de contenido y salida escapada por Angular. |
| Token almacenado de forma insegura | Secuestro de sesión | Usar mecanismo aprobado; no roles/tokens persistentes en `localStorage`. |
| Confusión de origen o CSRF | Operaciones no deseadas | CORS restringido, cookies seguras si se usan, validación de origen y CSRF según transporte. |
| IDOR entre reservas, alumnos o pagos | Acceso a recursos ajenos | Backend verifica `sub`, `gymId`, `classId`, `reservationId` y alcance. |
| Capacidades demasiado amplias | Privilegio excesivo | Matriz de mínimo privilegio y revisiones de cambios. |
| Claims obsoletos durante la sesión | Autorización desactualizada | Backend puede revocar/rechazar y frontend manejar sesión expirada. |
| Regla diaria calculada en zona incorrecta | Reservas duplicadas | Usar `America/Asuncion` y fecha de negocio backend. |
| WOD futuro visible por error | Fuga de contenido | Backend filtra por estado y fecha de publicación. |
| Reintentos duplican pagos o reservas | Inconsistencia financiera | Idempotencia, transacciones y claves de idempotencia. |
| Logs con datos personales | Fuga de información | Minimizar logs, enmascarar identificadores y no registrar tokens. |
| Dependencias no revisadas | Riesgo de cadena de suministro | Aprobación de paquetes, lockfile y actualizaciones controladas. |
| Costos AWS imprevistos | Superación del presupuesto | Arquitectura serverless, alertas y revisión antes de desplegar. |

   - Vacío, carga, acceso denegado, sesión expirada y error.
   - Sin tablas con datos ficticios.
4. **7B.4 — Estructuras por rol**
   - Componentes provisionales para las áreas ADMIN, COACH, STUDENT y COMMUNITY_MANAGER.
   - Sin servicios, backend, CRUD ni datos reales.
5. **7B.5 — Accesibilidad y responsive**
   - Validar 320, 768 y 1440 px.
   - Validar foco, Escape, Tab/Shift+Tab, contraste y reducción de movimiento.
6. **7B.6 — Pruebas de arquitectura**
   - Matriz de capacidades.
   - Rutas futuras y ausencia de rutas privadas funcionales.
   - Ausencia de datos privados simulados.
   - Regresión de rutas públicas y foco.

La integración real de Cognito, backend y operaciones de negocio será un incremento posterior, no un atajo dentro de 7B.

## 12. Condiciones de implementación y pruebas

### 12.1 Condiciones previas

Antes de implementar código privado se requiere:

- aprobación del diseño de Cognito y de los redirect URIs;
- contrato backend/versionado para sesión y capacidades;
- definición de claims o mecanismo de autorización;
- política de CORS y transporte de sesión;
- revisión de costos AWS;
- confirmación de que no se reutilizarán datos personales ni contenidos no aprobados;
- aceptación de que los guards son solo UX.

### 12.2 Pruebas mínimas de NP-003.7A/7B

- Matriz de capacidades: todos los roles y capacidades están tipados y cubiertos.
- Rutas futuras: las rutas privadas no aparecen como funcionales en la configuración pública actual.
- `/portal` informativo: no renderiza datos internos ni login ficticio.
- Ausencia de datos privados simulados: no hay alumnos, pagos, reservas ni usuarios ficticios.
- Regresión pública: `/`, `/gimnasio`, `/instalaciones`, `/entrenadores`, `/horarios`, `/actividades`, `/contacto`, `/acceso-alumnos` y 404 siguen accesibles.
- Foco: la navegación pública conserva el foco en `#contenido-principal`.
- Accesibilidad: foco visible, orden de teclado, Escape, menú responsive y contraste.
- Seguridad futura: no autenticado, denegado, expirado y backend 401/403 tienen comportamientos diferenciados.
- Idempotencia y reglas de negocio: pruebas backend separadas antes de exponer operaciones críticas.

Comandos de validación del frontend:

```bash
cd frontend
npm run build
npm test -- --watch=false
git diff --check
```

### 12.3 Criterios de aceptación de seguridad

NP-003.7 no podrá declararse seguro ni listo para producción hasta que:

- Cognito esté configurado con Authorization Code + PKCE;
- el backend valide JWT y capacidades;
- no existan rutas privadas accesibles sin autenticación real;
- no haya roles ni tokens ficticios en el cliente;
- las operaciones críticas tengan autorización backend, idempotencia y auditoría;
- se complete una revisión humana de seguridad y accesibilidad;
- se aprueben dominio, CORS, correo, contenido, costos y despliegue.
