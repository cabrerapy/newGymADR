## 1. Arquitectura recomendada

### 1.1 Decisión

Se recomienda implementar el portal privado con un **Backend for Frontend (BFF)** en Lambda Node.js 24/TypeScript:

```text
Navegador Angular
  |
  | cookie de sesión opaca (HttpOnly, Secure, SameSite)
  v
CloudFront / dominio público aprobado
  |
  | comportamiento /api/*
  v
API Gateway HTTP API
  |
  v
Lambda BFF
  |                 |
  | sesión/refresh  | OAuth 2.0 Authorization Code + PKCE
  v                 v
DynamoDB de autenticación       Amazon Cognito User Pool
  |
  v
DynamoDB de aplicación: usuarios, membresías, asignaciones y recursos
```

El navegador **no recibe** access tokens, ID tokens ni refresh tokens de Cognito. Angular solo recibe una cookie de sesión opaca y respuestas JSON mínimas. Lambda intercambia el código OAuth, valida los tokens, mantiene el estado de sesión y consulta la base de la aplicación antes de autorizar cualquier operación.

### 1.2 Fronteras de confianza

1. Angular es un cliente público. Sus guards, roles y capacidades son UX, no autorización.
2. La cookie prueba la existencia de una sesión BFF; no concede por sí sola una capacidad.
3. Cognito prueba la autenticación y emite identidad. Sus grupos o claims no son la política definitiva de negocio.
4. Lambda es la frontera de autorización efectiva para las rutas browser del BFF.
5. API Gateway aplica TLS, CORS, límites de método/tamaño, throttling y validación de borde; no sustituye las comprobaciones de sesión, usuario, capacidad o recurso en Lambda.
6. Una respuesta 2xx del BFF es la única confirmación de que una operación fue autorizada y ejecutada.
7. Los secretos de Cognito, las claves de cifrado y los refresh tokens nunca se escriben en el repositorio, URLs, cookies, `localStorage`, `sessionStorage`, métricas o logs.

### 1.3 Reconciliación con NP-001.2

NP-001.2 establece Cognito, API Gateway HTTP API, Lambda Node.js 24, DynamoDB on-demand y validación JWT. Este diseño no contradice esa base:

- Para el **portal browser**, el JWT se valida dentro del BFF y la ruta HTTP API correspondiente no usa un autorizador JWT como frontera principal; Lambda resuelve la cookie y la sesión.
- Para futuros clientes no browser aprobados, se podrá mantener una ruta o audiencia separada con autorizador JWT de API Gateway. Esa vía no comparte la cookie del portal ni hereda sus capacidades.
- DynamoDB conserva el modelo on-demand y las operaciones condicionales/transaccionales del baseline.
- La arquitectura continúa siendo serverless, en una sola región de referencia `us-east-1`, sin VPC, NAT, EC2, RDS, Fargate, provisioned concurrency ni WAF en el primer incremento.

La diferencia es una refinación de la frontera de confianza: el navegador deja de ser portador de bearer tokens y Lambda pasa a ser el único consumidor browser de la identidad OIDC.

### 1.4 Compatibilidad contractual

El diseño preserva Angular 22, componentes `standalone`, `OnPush`, carga perezosa y modelos tipados; los cuatro roles `ADMIN`, `COACH`, `STUDENT` y `COMMUNITY_MANAGER`; `PortalCapability`, `CapabilityScope` y `RoleCapabilityDefinition`; la matriz de NP-003.7A; `/portal` informativo; las rutas públicas actuales; la separación de shells; los targets `#contenido-principal` y `#portal-contenido-principal`; y el baseline Lambda/CDK y DynamoDB previsto.

No se modifica `frontend/`, `backend/`, `infra/`, Docker, DynamoDB, SEO, rutas, `NavigationFocusService` ni archivos de presentación.

### 1.5 Fuentes de verdad y no duplicación

- NP-001.2 y ADR-ARCH-001, ADR-COST-001 y ADR-DB-001 son restricciones arquitectónicas y económicas.
- NP-003.7A es la fuente de la matriz de capacidades y reglas de alcance.
- NP-003.7B es la fuente de la presentación no operativa y de la compatibilidad visual/accesible.
- NP-003.7C.1 es el contrato consolidado en el commit `0f3301b`.
- Los literales de roles y capacidades no se copian en el BFF. La implementación futura debe consumir una política versionada derivada de la matriz aprobada o un paquete/contrato neutral generado a partir de ella. Hasta entonces, el backend valida los valores contra el contrato versionado y tests de paridad; no crea una segunda matriz UI independiente.

### 1.6 Supuestos de diseño

1. La comunicación browser-BFF será HTTPS en producción.
2. El primer incremento es de solo lectura y no habilita reservas, pagos, asistencia ni escrituras de negocio.
3. La zona de negocio para WOD y reglas diarias es `America/Asuncion`.
4. El usuario de Cognito debe tener una identidad de aplicación activa y provisionada en DynamoDB antes de obtener sesión BFF.
5. Los valores propuestos de timeout y concurrencia son contratos pendientes de aprobación, no configuración aplicada.

## 2. Flujo de autenticación recomendado

### 2.1 Clasificación de endpoints

| Clase | Endpoints | Tratamiento |
|---|---|---|
| Públicos de autenticación | `GET /auth/start`, `GET /auth/callback` | No requieren sesión. Crean o consumen una transacción opaca de corta duración. Deben tener `Cache-Control: no-store`, límites de tasa y validación estricta de parámetros. |
| Mutación autenticada | `POST /auth/logout` | Requiere sesión válida o permite logout idempotente cuando la sesión ya expiró. Requiere CSRF, origen permitido y rotación/revocación. |
| Sesión/proyección | `GET /me`, `GET /me/capabilities` | Requieren sesión BFF activa y usuario de aplicación activo. No son públicos y no se cachean en una caché compartida. |

`GET /health` puede permanecer público para disponibilidad, pero no debe revelar estado de Cognito, DynamoDB, versiones internas ni secretos.

### 2.2 Secuencia de login

```mermaid
sequenceDiagram
    autonumber
    participant A as Angular
    participant B as Lambda BFF
    participant S as DynamoDB auth
    participant C as Cognito
    participant U as Usuario

    A->>B: GET /auth/start?returnTo=<ruta-relativa-aprobada>
    B->>B: validar origen, returnTo, método y límites de tasa
    B->>B: generar state, nonce y code_verifier (CSPRNG)
    B->>S: crear AUTH_TX#hash(state), TTL corto, estado pending
    B-->>A: 302/303 Location: Cognito authorization endpoint
    A->>U: navegador muestra hosted UI/MFA
    U->>C: autentica y aprueba scopes mínimos
    C->>A: GET /auth/callback?code=<one-time>&state=<state>
    A->>B: GET /auth/callback
    B->>S: leer y consumir AUTH_TX de forma condicional
    B->>B: comparar state, nonce esperado y redirect_uri exacto
    B->>C: token exchange con code_verifier y cliente confidencial
    C-->>B: token set (ID/access/refresh)
    B->>B: validar firma, iss, aud, exp, iat, nonce, scopes y algoritmo
    B->>S: consultar/provisionar identidad y crear sesión cifrada
    B-->>A: Set-Cookie __Host-adr_session; 302/303 retorno validado
    A->>B: GET /me y GET /me/capabilities con cookie
    B->>S: leer sesión, comprobar expiración/revocación
    B->>S: consultar usuario, rol efectivo y capacidades
    B-->>A: proyección mínima JSON
```

### 2.3 Pasos y garantías

1. **Inicio.** Angular navega a `/auth/start` con un retorno relativo opcional. El BFF no acepta un dominio, URL absoluta, rol, capacidad ni `gymId` enviados por el navegador.
2. **Material efímero.** Se generan `state`, `nonce` y `code_verifier` con un CSPRNG. `state` y `nonce` tienen al menos 128 bits de entropía; `code_verifier` sigue el formato PKCE aprobado. Se almacenan solo en una transacción server-side cifrada y de TTL corto.
3. **Redirección.** El BFF construye la solicitud OIDC con `response_type=code`, cliente aprobado, scopes mínimos, `redirect_uri` exacto, `state`, `nonce` y `code_challenge=S256(code_verifier)`. La URL de Cognito es un placeholder pendiente de aprobación; no se registra un dominio inventado.
4. **Callback y state.** El callback acepta solo HTTPS, un código y un state presentes. La transacción se consume con una escritura condicional para impedir reutilización. Un state ausente, duplicado, expirado o no vinculado al cliente produce 400/401 genérico y evento de auditoría.
5. **Intercambio del código.** Lambda envía el código, redirect URI, `client_id`, secreto del cliente confidencial y `code_verifier` directamente a Cognito. El código es one-time; el secreto nunca llega al navegador ni a logs. Si Cognito no soportara la combinación aprobada de cliente confidencial y PKCE, se detiene la implementación hasta corregir la configuración.
6. **Validación de tokens.** Se valida la firma con JWKS y `kid`, algoritmo permitido, `iss`, `aud`, `exp`, `iat`, `nonce`, scopes solicitados y estado del token. No se confía en un JWT sin validar ni en claims enviados por Angular.

## 3. Diagrama de sesión, recuperación y renovación

```mermaid
sequenceDiagram
    autonumber
    participant A as Angular
    participant B as Lambda BFF
    participant S as DynamoDB auth
    participant C as Cognito
    participant D as DynamoDB app

    A->>B: GET /me (cookie opaca)
    B->>S: HMAC(sessionId) + GetItem
    alt sesión ausente o expirada
        S-->>B: no existe / expiración efectiva vencida
        B-->>A: 401 SESSION_EXPIRED; limpiar cookie
    else activa
        S-->>B: item activo, versión N
        B->>B: comprobar idle/absoluta/revocation y descifrar tokens
        B->>D: consultar usuario, estado, membresía y asignaciones
        D-->>B: identidad y contexto verificados
        B-->>A: 200 proyección mínima
    end

    opt access token próximo a expirar
        B->>S: UpdateItem condicional version=N, single-flight
        S-->>B: versión N+1 / token set cifrado
        B->>C: refresh token rotated
        C-->>B: nuevo token set
        B->>S: Put/Update condicional con tokens cifrados
        B-->>A: respuesta de sesión renovada; cookie opcionalmente rotada
    end

    A->>B: POST /auth/logout (cookie + CSRF)
    B->>S: UpdateItem condicional: revokedAt/version
    B->>C: revoke refresh token
    B-->>A: limpiar cookie + 204/303 logout Cognito
```

La sesión se considera activa solo mientras Lambda pueda leerla y todas sus comprobaciones temporales pasen. DynamoDB puede tardar en borrar un item por TTL; esa demora no prorroga la sesión.

## 4. Almacenamiento de sesiones

### 4.1 Evaluación: tabla existente frente a tabla independiente

| Opción | Ventajas | Riesgos / costos | Decisión |
|---|---|---|---|
| Reutilizar la tabla DynamoDB de aplicación | Menos tablas, posible menor operación inicial, comparte backups/PITR | Mezcla fronteras de seguridad y ciclos de vida; IAM más amplio; riesgo de exponer tokens a operaciones de negocio; TTL y modelos distintos; evolución/acceso concurrente acoplados | No recomendada para tokens de sesión en el primer incremento |
| Tabla independiente de autenticación | IAM mínimo, esquema y TTL propios, blast radius reducido, auditoría y revocación claras, puede cifrarse y respaldarse según sensibilidad | Una tabla y log group adicionales; lecturas/escrituras de sesión separadas; decisión de residencia y costos pendiente | **Recomendada** para el BFF |

La tabla independiente no duplica el modelo de usuario: almacena una referencia opaca a la identidad (`cognitoSub` o ID de aplicación pseudonimizado), no una segunda copia editable de roles, membresías o capacidades. La fuente de verdad de negocio permanece en la tabla de aplicación.

### 4.2 Esquema lógico propuesto

```text
Table: <AUTH_SESSION_TABLE> (on-demand; nombre pendiente)
PK: SESSION#<HMAC-SHA-256(sessionId)>
SK: META

attributes:
  sessionIdHash        # solo hash; nunca el identificador completo
  cognitoSubHash       # referencia pseudonimizada; no email
  applicationUserId    # ID interno o referencia cifrada, según política
  status               # ACTIVE | REVOKED | EXPIRED
  version              # entero monótono
  createdAt
  lastSeenAt
  idleExpiresAt        # última actividad + idle timeout
  absoluteExpiresAt    # límite absoluto desde login
  effectiveExpiresAt   # menor de idle, absoluta y revocación programada
  ttl                  # epoch seconds para limpieza; >= effectiveExpiresAt + grace
  revokedAt?
  revocationVersion    # entero; incrementa en revocación
  tokenSetCiphertext   # envelope-encrypted; acceso IAM restringido
  tokenSetEncryptedMetadata
  authnContextHash     # MFA/amr/policy context mínimo, no secretos
  clientMetadataHash   # opcional; no fingerprinting invasivo
  auditPartition       # valor no sensible para trazabilidad
```

Transacciones OIDC efímeras, separadas de la sesión:

```text
PK: AUTH_TX#<HMAC-SHA-256(state)>
SK: META
stateHash, codeChallengeHash, nonceHash, codeVerifierCiphertext,
redirectUriHash, returnToRelative, createdAt, expiresAt, ttl,
status=PENDING|CONSUMED|FAILED, consumedAt, failureReasonCode
```

`state` viaja por la URL del callback, pero la tabla guarda solo su hash. `code_verifier` se cifra en la transacción y se elimina al consumir el código. El código OAuth nunca se persiste después del intercambio.

## 5. Contratos de endpoints del BFF

Todos los contratos son propuestas versionadas y no implican que las rutas existan en el HEAD actual. Las respuestas privadas usan UTF-8, un `requestId` opaco y un envelope estable; no incluyen tokens, cookies, claims crudos, emails, stack traces ni nombres de recursos internos.

### 5.1 `GET /auth/start`

**Clase:** público de autenticación; no requiere cookie de sesión.

**Entrada:** query opcional `returnTo`, limitada a una ruta relativa allowlist dentro del portal. Se rechazan URL absolutas, esquemas no HTTPS, `//host`, credenciales, fragmentos y rutas no permitidas.

**Comportamiento:** valida límites de tasa y origen; genera material efímero; persiste la transacción con TTL corto; responde `303 See Other` con `Location` hacia el endpoint de autorización de Cognito. La transacción no se crea mediante un rol o capacidad recibido del navegador.

**Headers:** `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer` cuando sea compatible. No se usa caché compartida.

**Errores:** `400 INVALID_RETURN_TO` o `INVALID_REQUEST`; `429 RATE_LIMITED`; `503 IDENTITY_PROVIDER_UNAVAILABLE`. Los errores no revelan el redirect URI interno ni el motivo detallado de Cognito.

### 5.2 `GET /auth/callback`

**Clase:** público de autenticación; no requiere sesión previa.

**Entrada:** `code` y `state` requeridos. El callback no acepta `returnTo`, tokens, roles ni datos personales desde Cognito fuera del contrato OIDC aprobado.

**Comportamiento:** localiza la transacción por hash de `state`, verifica que esté `PENDING` y no expirada, la consume de forma atómica, compara el código y el nonce esperados, realiza el intercambio con PKCE y valida los tokens. Crea una sesión nueva y devuelve una cookie opaca. Responde `303` hacia el retorno relativo aprobado o hacia la raíz pública segura.

**Errores:** `400 INVALID_CALLBACK` para parámetros o estado malformados; `401 INVALID_STATE` para state ausente, expirado o reutilizado; `502 UPSTREAM_AUTHENTICATION_FAILED` para fallo controlado de Cognito; `503 IDENTITY_PROVIDER_UNAVAILABLE` para indisponibilidad transitoria. Un código reutilizado se trata como intento de replay y se audita sin detalle sensible.

### 5.3 `POST /auth/logout`

**Clase:** mutación autenticada; requiere sesión o es idempotente si ya fue revocada.

**Entrada:** cookie de sesión y token CSRF válido. No se acepta un identificador de sesión, rol o token en el cuerpo.

**Comportamiento:** valida origen y CSRF; marca la sesión revocada con escritura condicional; incrementa la versión de revocación; revoca el refresh token cuando la política y el App Client lo permitan; elimina la cookie con los mismos atributos de creación; registra auditoría. Después de la invalidación local, propone redirigir al logout de Cognito con un `post_logout_redirect_uri` aprobado.

**Respuesta:** `303 See Other` hacia el flujo de logout aprobado, o `204 No Content` para un cliente que no siga la redirección, según la decisión de integración. La invalidación local debe completarse antes de considerar exitoso el logout.

**Errores:** `401 AUTH_REQUIRED` si no hay sesión y la política no permite idempotencia; `403 CSRF_INVALID`; `503 IDENTITY_PROVIDER_UNAVAILABLE` si la revocación externa falla, con estado local ya revocado y mensaje que no exponga el token.

### 5.4 `GET /me`

**Clase:** requiere sesión BFF activa y usuario de aplicación activo.

**Respuesta 200:**

```json
{
  "data": {
    "user": {
      "id": "<application-user-id>",
      "displayName": "<display-name-minimo>",
      "roles": ["<server-derived-role>"],
      "gymId": "<server-verified-gym-id>"
    },
    "session": {
      "status": "authenticated",
      "expiresAt": "<ISO-8601-effective-expiry>"
    }
  },
  "meta": {
    "requestId": "<opaque-request-id>",
    "policyVersion": "authz-v1"
  }
}
```

Los campos personales son opcionales y se proyectan solo con finalidad aprobada. `roles` y `gymId` son derivados por Lambda, no leídos de una cookie o parámetro. `Cache-Control: no-store`; `Vary: Cookie, Origin` cuando corresponda.

**Errores:** `401 AUTH_REQUIRED`/`SESSION_EXPIRED`; `403 USER_INACTIVE` o `IDENTITY_NOT_PROVISIONED`; `404 IDENTITY_NOT_FOUND` si la política no crea identidades automáticamente; `503 IDENTITY_STORE_UNAVAILABLE`.

### 5.5 `GET /me/capabilities`

**Clase:** requiere sesión, usuario activo y capacidad de bootstrap `profile:read` en alcance `own`, o la regla equivalente aprobada.

**Respuesta 200:**

```json
{
  "data": {
    "userId": "<application-user-id>",
    "gymId": "<server-verified-gym-id>",
    "capabilities": [
      { "name": "<capability>", "scope": "own" }
    ],
    "asOf": "<ISO-8601-server-time>"
  },
  "meta": {
    "requestId": "<opaque-request-id>",
    "policyVersion": "capabilities-v1"
  }

```

Una capacidad ausente significa no concedida. La lista se invalida ante cambios de rol, estado, membresía, asignación, gimnasio o versión de política. No se devuelve la matriz completa ni reglas internas. `Cache-Control: no-store` en el primer incremento; cualquier caché futura debe ser privada, de vida corta y versionada.

**Errores:** `401` para sesión ausente o expirada; `403` para usuario inactivo o sin capacidad de bootstrap; `404` para identidad no encontrada; `503` para almacén de identidad/política indisponible.

### 5.6 Errores, redirecciones y límites

```json
{
  "error": {
    "code": "SESSION_EXPIRED",
    "message": "La sesión no está disponible.",
    "requestId": "<opaque-request-id>",
    "retryable": false
  }
}
```

- `401`: sesión ausente, inválida o expirada. Angular no reintenta indefinidamente; inicia un login nuevo si la ruta lo permite.
- `403`: identidad válida pero usuario inactivo, capacidad ausente, alcance insuficiente o relación con el recurso no verificada.
- `404`: se usa para identidad o recurso no encontrado cuando no revelar su existencia es parte de la política; no se usa para ocultar errores de autorización de forma inconsistente.
- `429`: rate limiting por ruta, IP de borde, cuenta y acción; aplica backoff y no bloquea el callback legítimo por límites excesivamente bajos.
- `5xx`: fallo temporal o interno; se registra con `requestId`, se evita reintentar mutaciones sin idempotencia y no se expone la causa interna.
- Las redirecciones posteriores a login/logout aceptan solo rutas relativas allowlisteadas o URIs registrados; nunca se usa un valor de navegador como URL absoluta.

## 6. Cookies, origen y CSRF

### 6.1 Política recomendada

La opción preferida es un **proxy o comportamiento same-origin** que exponga Angular y el BFF bajo el mismo origen público aprobado. Esto evita CORS credencial para las llamadas normales, permite una cookie host-only y reduce la superficie de confusión de origen. La ruta pública informativa y el portal privado conservan sus shells y targets de foco; el proxy no cambia SEO ni rutas de aplicación.

Cookie de sesión propuesta:

```text
Name: __Host-adr_session
Value: <256-bit opaque session id, base64url>
Path: /
Secure: true
HttpOnly: true
SameSite: Strict
Domain: omitido (host-only)
Max-Age/Expires: no mayor que absoluteExpiresAt; renovación controlada
```

El prefijo `__Host-` exige `Secure`, `Path=/` y ausencia de `Domain`; por eso solo es compatible con la opción same-origin/host único. La cookie no se marca `Public`, no se almacena en JavaScript y no se envía a Cognito. El nombre y la ruta son contractuales; el valor real se genera en runtime.

### 6.2 SameSite y dominios

- **Same-origin preferido:** `SameSite=Strict` es adecuado para fetches y navegación same-origin. El callback OIDC es una navegación de primer nivel desde Cognito y no depende de la cookie de sesión; el state server-side es la correlación segura. El retorno posterior al portal recibe la cookie ya establecida en la respuesta del BFF.
- **Mismo sitio con subdominios:** si la revisión de dominios obliga a usar subdominios del mismo sitio, se evaluará `SameSite=Lax` y un `Domain` mínimo explícito. Esta opción requiere pruebas de redirección, cookies y CSRF; no se activa por defecto.
- **Orígenes realmente distintos:** `SameSite=None; Secure` solo se considerará si una llamada credencial cross-origin es imprescindible. Exige CORS exacto, validación estricta de `Origin`, CSRF explícito y pruebas de navegadores; no es la recomendación inicial.
- No se inventa un dominio compartido. La decisión de dominio, certificado, CloudFront behavior y URI de Cognito queda pendiente de aprobación.

### 6.3 Rotación y eliminación

- La sesión recibe un identificador nuevo en login y, si la política lo exige, en renovación con cambio de privilegios o sospecha de replay.
- La cookie se rota con `Set-Cookie` atómico y una condición de versión; una petición concurrente con la versión anterior no puede reactivar la sesión.
- El logout elimina la cookie usando el mismo nombre, `Path`, `Domain` y atributos de seguridad. Una cookie `__Host-` se elimina sin `Domain`.
- El navegador no decide la expiración efectiva. Un `Max-Age` más largo que la sesión server-side no concede acceso; un `Max-Age` más corto solo puede cerrar la sesión antes.

### 6.4 Verificación de origen

Para solicitudes credenciales y mutables, Lambda/API Gateway deben aceptar únicamente un conjunto exacto de orígenes aprobados, comparando esquema, host y puerto. Se rechazan:

- `Origin` ausente cuando la política lo exige;
- múltiples valores o sintaxis inválida;
- orígenes no allowlisteados, subdominios no aprobados y coincidencias por sufijo;
- `Origin` inconsistente con `Sec-Fetch-Site`/modo de navegación cuando se use esa señal;
- redirecciones o retornos absolutos no registrados.

En navegaciones top-level (`GET /auth/start`, `GET /auth/callback`) el `Origin` puede no estar presente por diseño. En esos endpoints la garantía principal es el state/nonce, el consumo one-time, la validación de redirect URI y las señales de navegación aprobadas; no se finge una comprobación de origen imposible. Para `POST /auth/logout`, la ausencia o inconsistencia de `Origin` es motivo de rechazo.

### 6.5 Política CSRF

`HttpOnly` impide que JavaScript lea la cookie, pero **no elimina CSRF ni XSS**. La defensa es en capas:

1. `Secure`, `HttpOnly`, `SameSite` y origen mínimo.
2. Validación estricta de `Origin` para métodos inseguros.
3. Token CSRF de sesión, generado con CSPRNG, almacenado server-side como hash y entregado a Angular en una respuesta JSON autenticada (por ejemplo, como campo de bootstrap de `/me`), no en la cookie de sesión.
4. Angular envía el token en `X-CSRF-Token` en `POST`, `PUT`, `PATCH`, `DELETE` y cualquier método futuro no seguro.
5. Lambda compara el token con el hash vinculado a la sesión y versión; rota el token al rotar la sesión y lo invalida en logout/revocación.
6. Las mutaciones críticas futuras requieren además idempotencia y autorización de recurso; CSRF no sustituye ninguna de ellas.

`GET /auth/start` queda como excepción de navegación segura solo si se mantiene la recomendación GET y se aprueba su modelo de login CSRF. `GET /auth/callback` no lleva CSRF porque el state OIDC one-time es la defensa del flujo de retorno. Si `/auth/start` cambia a POST, requerirá CSRF o un formulario same-origin aprobado.

### 6.6 CORS y compatibilidad frontend/API

- Si se usa same-origin, las peticiones normales no requieren CORS; el proxy debe evitar caché compartida para `/auth/*`, `/me` y `/me/capabilities`.
- Si se mantiene una API cross-origin, API Gateway HTTP API debe configurar `AllowOrigins` con valores exactos, `AllowCredentials=true`, métodos y headers mínimos, y una ruta `OPTIONS` pública para preflight. No se usa `*` con credenciales. API Gateway puede responder preflight y, cuando hay configuración CORS, ignora headers CORS devueltos por Lambda.
- Angular usa `credentials: 'include'` solo en el cliente autorizado y un interceptor central para CSRF, 401/403 y estado de sesión. No guarda tokens, roles ni capacidades como fuente de autorización.
- Se rechazan solicitudes con cookie pero origen no autorizado, CSRF inválido, método no permitido, sesión revocada o identidad inactiva. La respuesta no debe revelar cuál de varias comprobaciones falló cuando esa distinción aumente el riesgo.

## 7. Autorización efectiva en Lambda

La autorización se ejecuta en cada petición privada y sigue una cadena de fallo cerrado. Angular puede ocultar controles, pero nunca participa en la decisión:

```text
request
  -> normalizar método, ruta, origen y requestId
  -> resolver cookie opaca
  -> leer y validar sesión
  -> validar token de acceso / renovar si corresponde
  -> resolver identidad de aplicación actual
  -> comprobar estado del usuario
  -> resolver roles efectivos server-side
  -> resolver capacidad y alcance requeridos
  -> comprobar gymId y relación con el recurso
  -> aplicar política versionada de mínimo privilegio
  -> ejecutar operación o devolver 401/403/404
  -> auditar decisión sin datos sensibles
```

### 7.1 Procedimiento obligatorio

1. **Contexto de borde.** API Gateway valida método, tamaño, esquema y throttling. Lambda genera un `requestId` opaco y normaliza ruta, método, origen y parámetros. Los valores de ruta/query se tratan como datos no confiables.
2. **Resolver identidad de sesión.** Se lee la cookie `__Host-adr_session`; se rechazan cookies duplicadas, mal formadas o con atributos inesperados. Se calcula el HMAC del identificador y se obtiene el item por clave exacta.
3. **Validar sesión.** Lambda comprueba `status=ACTIVE`, `effectiveExpiresAt > now`, versión, hash y `revocationVersion`. Una sesión revocada o expirada devuelve 401 y no continúa. La lectura se actualiza de forma atómica cuando la política exige extender `lastSeenAt`; una condición de versión evita carreras.
4. **Validar tokens.** El access token se valida localmente con JWKS, `kid`, algoritmo permitido, `iss`, `aud`, `exp`, `iat`, scopes y firma. El `nonce` se comprueba en el callback, no en cada petición. Si el access token está cerca de expirar, Lambda realiza una renovación controlada antes de continuar.
5. **Consultar estado actual.** El `cognitoSub` se mapea a una identidad de aplicación en DynamoDB. Lambda consulta estado activo/suspendido, gimnasio autorizado, membresía vigente y asignaciones actuales. No se usa un rol o `gymId` enviado por el navegador.
6. **Resolver rol efectivo.** Los roles se derivan de la identidad y la política server-side. Los grupos/claims de Cognito pueden ser una señal de entrada, pero no son la fuente definitiva. Cambios de rol o suspensión se reflejan en la siguiente petición o antes, según la versión de política aprobada.
7. **Resolver capacidad y alcance.** La ruta declara la capacidad requerida y el alcance (`gym`, `assigned`, `own`, `approved-public`). Lambda consulta la matriz versionada y aplica fallo cerrado: ausencia de capacidad equivale a denegación.
8. **Comprobar `gymId`.** El `gymId` efectivo proviene de la sesión/identidad y del recurso verificado. Si el recurso pertenece a otro gimnasio, se deniega aunque el rol tenga una capacidad amplia.
9. **Comprobar relación con el recurso.** Para `own`, se compara el propietario con el usuario; para `assigned`, se verifica clase/asignación vigente; para `gym`, se verifica membresía/autoridad dentro del gimnasio; para `approved-public`, se verifica estado de publicación y fecha de visibilidad. Se previenen IDOR/BOLA mediante claves compuestas y consultas acotadas.
10. **Mínimo privilegio.** La decisión final es `allow` solo si todas las comprobaciones pasan. No se conceden capacidades por defecto, no se amplía alcance por claims y no se devuelven recursos vecinos para ocultar una denegación.
11. **Auditoría.** Se registra `requestId`, acción, tipo/id pseudónimo de recurso, decisión, `gymId` verificado, capacidad, alcance, versión de política y motivo interno. No se registran tokens, cookie, código OAuth, refresh token, email, cuerpo completo ni stack trace.

### 7.2 Decisión y códigos

```text
allow
deny_missing_session       -> 401 AUTH_REQUIRED
deny_session_expired       -> 401 SESSION_EXPIRED
deny_session_revoked       -> 401 SESSION_REVOKED
deny_user_inactive         -> 403 USER_INACTIVE
deny_missing_capability    -> 403 FORBIDDEN
deny_out_of_scope          -> 403 FORBIDDEN
deny_resource_relation     -> 403 FORBIDDEN o 404 RESOURCE_NOT_FOUND
deny_store_unavailable     -> 503 IDENTITY_STORE_UNAVAILABLE
```

La elección entre 403 y 404 se define por recurso y se mantiene consistente para evitar enumeración. Las denegaciones se registran con la misma disciplina de minimización que los accesos autorizados.

### 7.3 Concurrencia y datos actuales

- Las renovaciones de una misma sesión usan una promesa/single-flight por instancia y una condición DynamoDB por versión.
- Si dos invocaciones leen la misma versión, una actualiza y la otra reintenta una vez con backoff limitado o usa la nueva versión; nunca se aceptan dos refresh tokens activos.
- La política y las asignaciones se consultan en su versión actual cuando la operación lo requiere. Una caché de autorización, si se aprueba, tendrá TTL corto y se invalida por versión de usuario, membresía, asignación, gimnasio o política.
- El navegador no recibe la decisión interna ni la matriz completa; solo recibe la proyección mínima necesaria para UX.

## 8. Revocación, renovación y logout

### 8.1 Estados y transiciones

```text
PENDING_AUTH -> ACTIVE -> EXPIRED
                    |        |
                    +-> REVOKED
```

- `PENDING_AUTH`: transacción OIDC o sesión incompleta; no autoriza ninguna petición privada.
- `ACTIVE`: sesión válida mientras no venza y no esté revocada.
- `EXPIRED`: `effectiveExpiresAt` vencido; se rechaza y se limpia de forma eventual por TTL.
- `REVOKED`: invalidación explícita por logout, suspensión, pérdida o incidente; vence cualquier acceso BFF inmediatamente.

La expiración no depende de que DynamoDB haya borrado el item. La revocación no depende de que Cognito haya confirmado la invalidación de un access token ya emitido.

### 8.2 Renovación controlada

1. Lambda detecta que el access token está dentro de una ventana segura antes de expirar.
2. Una única operación por sesión obtiene un lease/single-flight y lee la versión actual.
3. Si otra invocación renovó primero, se reutiliza la versión nueva y se evita un segundo refresh.
4. Lambda envía el refresh token a Cognito desde el entorno server-side, con timeout y reintento limitado.
5. Cognito devuelve un token set rotado; el BFF cifra y persiste la nueva versión con condición `version=N`.
6. La cookie solo se rota si la política exige nuevo `sessionId`; en cualquier caso, la versión de sesión y el CSRF se actualizan.
7. Si el refresh falla por revocación, expiración o error permanente, se marca la sesión revocada/expirada y se devuelve 401.
8. Si el fallo es transitorio, se mantiene la sesión solo hasta su expiración efectiva y se registra una alarma; no se reintenta en bucle.

El refresh token nunca se entrega a Angular, no se duplica en varias sesiones y no se guarda en cookies, URLs, localStorage, logs o trazas.

### 8.3 Logout

El logout se trata como una mutación autenticada e idempotente:

1. Angular cancela operaciones pendientes y evita doble envío.
2. El navegador envía `POST /auth/logout` con cookie y token CSRF.
3. Lambda valida origen/CSRF y marca la sesión `REVOKED` mediante escritura condicional.
4. Se incrementa la versión de revocación y se invalida el CSRF.
5. Se intenta revocar el refresh token en Cognito; el fallo externo no reactiva la sesión local.
6. Se elimina la cookie con los mismos atributos de creación.
7. Se registra un evento de auditoría con resultado local y resultado externo separados.
8. Se redirige al logout de Cognito con un `post_logout_redirect_uri` aprobado; el retorno final va a una ruta pública segura.
9. Angular limpia estado, capacidades y cualquier retorno; no conserva tokens ni roles.

### 8.4 Revocación global y respuesta a incidentes

- La suspensión o desactivación del usuario actualiza el estado en DynamoDB y aumenta una versión de revocación familiar.
- Un índice sparse por `cognitoSubHash` permite localizar sesiones activas sin scans; su creación y cardinalidad son decisiones pendientes.
- Ante pérdida de cookie, dispositivo comprometido o incidente, se revocan todas las sesiones del usuario y se fuerzan nuevos `sessionId`.
- Los access tokens ya emitidos pueden seguir siendo criptográficamente válidos hasta `exp`; por ello las rutas BFF comprueban sesión/revocación en cada petición y se recomienda un access token de vida corta.
- La revocación externa de Cognito se considera una defensa adicional, no la única frontera de validez.

## 9. Riesgos residuales y controles

| Riesgo residual | Impacto | Controles previstos | Estado / pendiente |
|---|---|---|---|
| XSS ejecuta acciones como el usuario | Alto | BFF oculta tokens; CSP estricta, escaping Angular, sanitización, Trusted Types cuando sea viable y revisión de dependencias | Residual alto; no asumir que `HttpOnly` elimina XSS |
| Robo o replay de cookie | Alto | `__Host-`, Secure, HttpOnly, SameSite, HMAC, vida corta, rotación, detección de anomalías y revocación | Residual medio; probar dominios y navegadores |
| CSRF en mutaciones | Alto | SameSite, Origin exacto, token CSRF por sesión, método POST y límites de tasa | Pendiente de implementación y pruebas |
| Login CSRF / confusión de flujo | Alto | state/nonce, redirect URI exacto, returnTo relativo, consumo one-time; decidir GET vs POST start | Pendiente de aprobación |
| Claims obsoletos o rol falso | Alto | Lambda deriva rol/capacidades de DynamoDB/política; no acepta roles del navegador | Control de diseño; validar paridad |
| IDOR/BOLA | Alto | Verificación de `gymId`, propietario, asignación, publicación y alcance; claves acotadas | Pendiente de pruebas cruzadas |
| Código OAuth o token en logs | Crítico | Redacción de logs, campos permitidos, pruebas de secreción y secretos en almacén cifrado | Pendiente de implementación |
| Error de validación JWT/JWKS | Alto | Algoritmos permitidos, `kid`, caché JWKS con refresh, `iss`/`aud`/`exp`/`nonce` | Pendiente de pruebas de rotación |
| Carrera de refresh/logout | Alto | versión monótona, condiciones DynamoDB, single-flight e idempotencia | Pendiente de pruebas de concurrencia |
| TTL borrado tarde | Medio | expiración efectiva server-side independiente del TTL | Diseñado; validar operación real |
| CORS o dominio mal configurado | Alto | same-origin preferido; orígenes exactos; sin wildcard credencial; pruebas de preflight | Pendiente de decisión de dominio |
| Webview o cliente no estándar | Medio/Alto | matriz de compatibilidad, pruebas SameSite/cookie; no prometer soporte no aprobado | Pendiente de producto |
| IAM/KMS demasiado amplio | Crítico | roles por función, tabla separada, cifrado envelope, sin scans y revisión IAM | Pendiente de CDK/seguridad |
| Logs con datos personales | Alto | minimización, pseudonimización, retención corta, alertas y acceso restringido | Pendiente de privacidad |
| Abuso de login/callback | Alto | rate limiting, throttling, MFA/CAPTCHA según riesgo, monitoreo y backoff | Pendiente de umbrales |
| Costos de renovación/sesiones | Medio | métricas por operación, alertas 50/75/90/100 %, tabla separada y Pricing Calculator | Pendiente de medición |
| Disponibilidad de Cognito/BFF | Alto | timeouts, circuit breaker, respuestas degradadas seguras, alarmas y plan de contingencia | Pendiente de SLO |
| Cambio de matriz de capacidades | Alto | versión de política, tests de paridad frontend/backend y revisión de cambios | Pendiente de gobernanza |

### 9.1 Principios de respuesta

- Fallar cerrado ante incertidumbre de sesión, identidad, política o recurso.
- No convertir un error de Cognito en un login automático sin validar el estado.
- No revelar si un usuario, recurso o gimnasio existe cuando eso facilite enumeración.
- Separar el motivo interno para auditoría del mensaje público estable.
- No registrar secretos ni datos personales para “facilitar diagnóstico”.
- Mantener el portal público y `/portal` informativo disponibles cuando el BFF esté indisponible, sin exponer datos privados.

## 11. Pruebas futuras

Las pruebas siguientes son criterios de validación para un incremento autorizado; no se ejecutan en este documento.

### 11.1 Autenticación y OIDC

- [ ] `state`, `nonce` y `code_verifier` se generan con CSPRNG y tienen entropía/tamaño aprobados.
- [ ] El callback sin `state`, con state expirado, duplicado o de otra transacción no crea sesión.
- [ ] Un código OAuth reutilizado se rechaza y genera auditoría de replay.
- [ ] El token exchange usa redirect URI exacto, PKCE y cliente confidencial; el secreto no aparece en código, logs, URL ni trazas.
- [ ] Se prueban JWKS con `kid` nuevo y antiguo, algoritmo no permitido, `iss`, `aud`, `exp`, `iat` y `nonce` inválidos.
- [ ] Un error de Cognito produce respuesta estable y no un login automático inseguro.
- [ ] `returnTo` absoluto, con credenciales, `//host`, esquema no HTTPS o ruta no allowlisteada se rechaza.
- [ ] Login/logout/redirección se prueban en historial, recarga, pestañas y botón atrás; el botón atrás no restaura contenido privado.

### 11.2 Sesión, concurrencia y revocación

- [ ] Sesión ausente, expirada, revocada y con hash inválido devuelve 401 sin revelar detalles.
- [ ] El TTL puede borrar tarde sin extender `effectiveExpiresAt`.
- [ ] Dos peticiones concurrentes no provocan dos refresh tokens activos.
- [ ] Dos logouts concurrentes son idempotentes y solo una revocación gana la condición.
- [ ] La rotación de sesión invalida la cookie anterior y no permite replay.
- [ ] La revocación global invalida todas las sesiones del usuario en la siguiente comprobación.
- [ ] Un access token criptográficamente válido no bypassa una sesión local revocada.
- [ ] La limpieza de memoria y la redacción de logs se verifican con pruebas de secreción.

### 11.3 Cookies, origen y CSRF

- [ ] La cookie tiene `Secure`, `HttpOnly`, `Path=/`, sin `Domain` cuando se usa `__Host-`, y `SameSite` aprobado.
- [ ] Un origen no autorizado, un `Origin` ausente en logout o un CSRF inválido recibe rechazo.
- [ ] CORS cross-origin acepta solo orígenes exactos, credenciales explícitas y preflight restringido; no hay wildcard credencial.
- [ ] La cookie no aparece en `document.cookie`, `localStorage`, `sessionStorage`, URL, logs ni métricas.
- [ ] Se prueban Chrome, Firefox, Safari, modo privado, móviles y webviews aprobadas.
- [ ] La eliminación de cookie usa exactamente nombre, ruta, dominio y atributos de creación.

### 11.4 Autorización y recursos

- [ ] Identidad válida sin capacidad obtiene 403 y presentación de acceso denegado.
- [ ] `ADMIN` accede solo al gimnasio autorizado, nunca a otro gimnasio.
- [ ] `COACH` accede únicamente a clases, alumnos, reservas, asistencia y WOD asignados.
- [ ] `STUDENT` accede solo a perfil, membresía, WOD y reservas propios.
- [ ] `COMMUNITY_MANAGER` accede solo a contenido/galería/actividades públicos aprobados.
- [ ] Un `gymId` o rol enviado por el navegador no amplía privilegios.
- [ ] Claims obsoletos tras suspensión o cambio de rol producen decisión actualizada.
- [ ] Las pruebas IDOR/BOLA cubren propietario, asignación, gimnasio, publicación y fecha.
- [ ] 401/403/404 usan envelope estable, `requestId` y mensajes no sensibles.

### 11.5 Integración, costos y operación

- [ ] `/me` y `/me/capabilities` no devuelven tokens, claims crudos ni matriz de otros roles.
- [ ] El primer incremento de solo lectura no expone reservas, pagos, asistencia ni escrituras.
- [ ] Se miden latencia, errores, throttling, renovaciones, lecturas/escrituras y logs por escenario.
- [ ] El presupuesto real se compara con US$ 15/20 y se ajustan supuestos antes de producción.
- [ ] Alarmas 50/75/90/100 %, retención, acceso a logs y procedimiento de incidentes están probados.
- [ ] La compatibilidad con portal público, `/portal`, Angular standalone y focos `#contenido-principal`/`#portal-contenido-principal` se verifica sin modificar el servicio actual en este incremento.

## 12. Decisiones pendientes de aprobación

1. **Frontera de dominio:** mismo origen mediante proxy/CloudFront behavior frente a API cross-origin; dominio público, API, Cognito y redirect URIs exactos.
2. **Método de inicio:** mantener `GET /auth/start` para navegación directa o cambiar a `POST` con protección login CSRF; efecto en accesibilidad e historial.
3. **Cognito:** app client confidencial y PKCE soportado por la configuración aprobada, scopes, MFA, recuperación, duración de tokens, refresh y logout.
4. **Sesión:** idle timeout, máximo absoluto, grace de limpieza, número máximo de sesiones, rotación de cookie y política de renovación.
5. **Almacenamiento:** nombre/región de tabla independiente, GSI de revocación, KMS, retención/PITR y tamaño máximo de item.
6. **CSRF/CORS:** token CSRF, headers, orígenes exactos, `SameSite` para subdominios y compatibilidad webview.
7. **Autorización:** fuente definitiva de roles, provisioning de identidad, versión de matriz, caché y tratamiento de claims obsoletos.
8. **Privacidad:** campos proyectados, residencia, retención, acceso de soporte, aviso/consentimiento y pseudonimización.
9. **Costos:** región, precios de transferencia, KMS/Secrets Manager, métricas/alarms, free tier y aceptación del impacto incremental.
10. **Seguridad adicional:** WAF, MFA avanzado, SMS, rate limits concretos, SLO y respuesta a incidentes.
11. **Compatibilidad de foco:** mecanismo común para los dos targets antes de cualquier cambio futuro a `NavigationFocusService`.
12. **Primer incremento:** aprobación de un único endpoint de lectura de bajo riesgo y de los criterios de salida antes de implementar código operativo.

## 13. Plan para el primer incremento implementable

## 14. Verificación de compatibilidad y alcance

### 14.1 Integración posterior sin ruptura

El diseño se integra posteriormente sin romper:

- **Portal público:** las rutas y el shell público continúan siendo independientes; el BFF solo atiende la frontera privada aprobada.
- **`/portal` informativo:** permanece sin datos privados ni login funcional hasta una fase autorizada.
- **Matriz de capacidades:** se conserva como fuente de nombres/alcances; Lambda aplica la versión server-side y Angular solo proyecta UX.
- **Angular standalone:** el cliente puede usar un interceptor central, `credentials: 'include'` y estados observables sin cambiar el modelo de autorización.
- **Roles existentes:** `ADMIN`, `COACH`, `STUDENT` y `COMMUNITY_MANAGER` se conservan; ningún rol viaja como fuente de autorización.
- **Modelo DynamoDB previsto:** la tabla de aplicación conserva single-table, GSI sparse, conditional writes y transacciones; la tabla de autenticación es una frontera separada.
- **NavigationFocusService:** no se modifica; el diseño futuro debe resolver los targets mediante una frontera común.
- **Arquitectura Lambda/CDK:** BFF bajo demanda, HTTP API, DynamoDB on-demand, CloudWatch y una sola región; sin recursos premium no aprobados.
