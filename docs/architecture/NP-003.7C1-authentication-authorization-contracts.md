## 2. Decisión de arquitectura recomendada

### 2.1 Decisión

Se recomienda implementar el portal privado con la alternativa **B. Backend for Frontend (BFF) con sesión segura mediante cookies HttpOnly**.

El navegador Angular no recibe access tokens, ID tokens ni refresh tokens de Cognito. Recibe solo una cookie de sesión opaca, con atributos de seguridad, mientras el BFF mantiene el estado de sesión y los tokens en el servidor. El BFF valida la sesión en cada petición, consulta la base de datos de la aplicación y devuelve proyecciones mínimas al frontend.

La recomendación no se basa en la facilidad de implementación. Se fundamenta en reducir la superficie de robo de tokens ante XSS, evitar refresh tokens persistentes en el navegador, simplificar renovación y logout, permitir CORS estricto con credenciales, centralizar la autorización efectiva en Lambda y conservar una arquitectura serverless económica.

La alternativa SPA/PKCE sigue siendo válida para clientes públicos o integraciones que no puedan usar cookies, pero no es la opción recomendada para este portal web privado.

### 2.2 Fronteras de confianza

```text
Navegador Angular
  |
  | cookie de sesión opaca (HttpOnly, Secure, SameSite)
  v
BFF Lambda + API Gateway HTTP API
  |                 |
  | sesión/refresh  | JWT directo solo para clientes no browser aprobados
  v                 v
DynamoDB de sesión   Validación Cognito/JWKS
  |
  v
DynamoDB de aplicación: usuarios, membresías, asignaciones y reglas

BFF <--- OAuth 2.0 Authorization Code + PKCE ---> Cognito User Pool
```

Reglas de confianza:

1. El navegador es un cliente público y nunca es una frontera de autorización.
2. La cookie de sesión prueba que existe una sesión del BFF; no prueba por sí sola capacidades ni acceso a un recurso.
3. Cognito prueba autenticación y emite identidad; no decide capacidades de negocio.
4. Lambda es la frontera de autorización efectiva y consulta el estado actual en la base de datos.
5. Una respuesta HTTP 2xx del backend es la única confirmación de autorización efectiva.
6. Un guard Angular puede mejorar la experiencia de navegación, pero nunca concede acceso.

## 3. Comparación de alternativas

| Criterio | A. SPA Angular + Authorization Code + PKCE | B. BFF + cookies HttpOnly | Consecuencia para ADR Cross |
|---|---|---|---|
| Seguridad frente a XSS | El código del portal puede acceder a tokens mientras estén en memoria; un XSS puede exfiltrar access/refresh tokens o invocar APIs como el usuario. | Los tokens permanecen en Lambda; JavaScript no puede leerlos. Un XSS todavía puede actuar dentro de la sesión, por lo que CSP, sanitización y aislamiento siguen siendo obligatorios. | B reduce el impacto de robo de credenciales, pero no elimina XSS. |
| Exposición y persistencia de tokens | Access token normalmente en memoria; refresh token puede quedar en memoria o en una cookie no HttpOnly según diseño. Persistencia en `localStorage` queda prohibida. | Refresh/access/ID tokens se almacenan solo en sesión server-side cifrada; el navegador recibe una cookie opaca. | B ofrece mejor contención de secretos. |
| CSRF | Con bearer token en header y CORS estricto, el riesgo CSRF es menor; sigue siendo necesario validar origen y no usar cookies credenciales sin protección. | Las cookies se envían automáticamente; se requieren `SameSite`, validación de `Origin`/`Referer` y token CSRF para métodos inseguros. | B añade un control explícito, pero manejable. |
| Complejidad operativa | Menos componentes server-side; depende de una biblioteca OIDC aprobada y de una gestión cuidadosa de renovación concurrente. | Requiere endpoints de login/callback/logout, sesión server-side, rotación de cookie, CSRF y almacenamiento/revocación de refresh tokens. | B es más complejo de implementar y operar. |
| Costos AWS | Cognito MAU, HTTP API, Lambda y DynamoDB de aplicación; menos lecturas/escrituras de sesión. | Los mismos servicios base más lecturas/escrituras de sesión, callbacks y posible función/log group BFF. | B puede incrementar uso de Lambda/DynamoDB/CloudWatch; debe medirse antes de aprobar. |
| HTTP API + Lambda | Compatible; el cliente envía `Authorization: Bearer` y API Gateway puede usar autorizador JWT. | Compatible; el cliente envía cookie y Lambda resuelve la sesión. API Gateway puede manejar CORS/cookies, pero la autorización de sesión corresponde a Lambda. | Ambas encajan; B centraliza mejor la política. |
| CORS | API cross-origin con orígenes exactos, headers `Authorization` y métodos aprobados; no comodines con credenciales. | Puede operar same-origin o con orígenes exactos y `credentials`; la cookie exige una política más estricta. | B facilita una frontera de origen clara si el dominio está definido. |
| Renovación | Cada tab puede renovar; hay que evitar carreras de refresh y exponer errores de forma uniforme. | El BFF renueva una sola vez, consolida respuestas y mantiene una sesión coherente. | B mejora experiencia y control de fallos. |
| Logout | Limpiar estado del cliente y llamar al logout de Cognito; los tokens ya emitidos pueden seguir válidos hasta expirar. | Revocar sesión/refresh, eliminar cookie y sesión server-side, luego redirigir al logout de Cognito; permite invalidación centralizada. | B ofrece logout más verificable. |
| Mobile-first | Funciona en navegadores móviles; tokens en memoria y redirecciones deben cuidarse en webviews y pestañas. | Cookies pueden tener limitaciones en webviews o contextos de terceros; se requiere probar SameSite, dominio y redirecciones. | B es preferible en navegador estándar; las webviews quedan como decisión abierta. |
| Experiencia de carga inicial | El cliente puede consultar sesión y lanzar varias renovaciones si no se coordina. | Una única llamada `/me` o bootstrap resuelve sesión, usuario y capacidades. | B simplifica el shell privado. |

### 3.1 Ventajas y limitaciones de la recomendación BFF

**Ventajas:** tokens fuera del navegador, renovación centralizada, logout y revocación más fuertes, autorización y reglas de negocio en un único boundary server-side, CORS restringido y menor probabilidad de que un rol falso en el cliente llegue a producción.

**Limitaciones:** mayor superficie de código backend, necesidad de una sesión server-side durable, protección CSRF, pruebas de cookies en dominios y móviles, y mayor dependencia de la disponibilidad del BFF para cada operación.

**Riesgos residuales:** XSS puede realizar acciones como el usuario; una cookie robada mediante vulnerabilidades del navegador o malware puede reutilizarse dentro de su ventana; una sesión server-side comprometida o mal revocada puede mantener acceso; un CSRF mal implementado puede ejecutar métodos inseguros; una webview puede no cumplir las expectativas de cookies de primer dominio.

### 3.2 Condición para reconsiderar SPA/PKCE

Solo se reconsiderará A si existe un requisito aprobado de clientes sin cookies, una restricción de dominio que impida el BFF, o una validación de seguridad que demuestre que los tokens pueden mantenerse exclusivamente en memoria con renovación coordinada, sin refresh token persistente, y que el costo/operación de BFF excede el presupuesto. Incluso entonces, los guards Angular seguirán siendo solo UX.

## 4. Identidad Cognito

### 4.1 Recursos lógicos

Se utilizará un **User Pool** como directorio de identidad y uno o más **App Clients** según la frontera aprobada:

- un App Client confidencial para el BFF, con secreto almacenado fuera del repositorio y sin exposición al navegador;
- opcionalmente, un App Client público para clientes no browser aprobados; no se usará un cliente público para entregar refresh tokens al Angular BFF;
- scopes OAuth mínimos y explícitos; no se usarán scopes genéricos como autorización de negocio;
- hosted UI o dominio de OAuth pendiente de aprobación; no se inventa un dominio en este documento.

El baseline CDK ya declara un User Pool y un App Client, pero su configuración actual no demuestra Authorization Code + PKCE ni los redirect URIs requeridos. Deberá corregirse en una fase autorizada, sin reutilizar credenciales ni identificadores ficticios.

### 4.2 Flujo Authorization Code + PKCE

1. Angular redirige al usuario a un endpoint BFF de inicio de login, nunca directamente con parámetros de rol o permisos.
2. El BFF genera `state`, `nonce` y `code_verifier` con un generador criptográfico seguro; guarda el challenge y los valores efímeros en sesión server-side.
3. El BFF redirige a Cognito con `response_type=code`, client_id aprobado, redirect_uri exacto, scopes mínimos, `state`, `nonce` y `code_challenge`.
4. Cognito autentica y aplica MFA/política de riesgo aprobadas; devuelve un código al redirect URI permitido.
5. El BFF verifica que el estado corresponde a la sesión iniciada, evita replay y exchangea el código con PKCE usando el App Client confidencial.
6. El BFF valida ID token, access token y refresh token según el contrato; crea una sesión opaca y devuelve una cookie nueva.
7. Angular consulta `/me` y `/me/capabilities`; nunca lee tokens ni claims crudos como fuente de autorización.

`state` protege contra CSRF y confusión de flujo; `nonce` vincula el ID token con la autenticación iniciada; `code_verifier` y `code_challenge` protegen el intercambio del código. El `code_verifier` no se guarda en `localStorage`, URL persistente, logs ni estado navegable.

### 4.3 Redirect URI, callback y logout

- Los redirect URIs serán HTTPS, exactos, de origen aprobado y registrados en Cognito; no se usarán comodines.
- El callback del BFF aceptará solo el estado de una sesión activa y rechazará códigos reutilizados, estados ausentes o redirecciones abiertas.
- El logout será una operación server-side que invalida la sesión, revoca el refresh token cuando la política lo exija, elimina la cookie y redirige al endpoint de logout de Cognito con un post-logout URI aprobado.
- No se confiará en un parámetro `returnTo` no validado. Solo se aceptarán rutas relativas allowlisteadas dentro del portal.
- El dominio de Cognito, el dominio público, el dominio de API y los URI exactos son decisiones pendientes; no se registran valores inventados.

### 4.4 Tokens

| Token | Contenido mínimo | Uso y custodia |
|---|---|---|
| Access token | JWT de vida corta con `token_use=access`, `sub`, `iss`, `aud`, `exp`, scopes y claims configurados. | El BFF lo valida y lo usa internamente; nunca se entrega al Angular. |
| ID token | JWT de identidad con `token_use=id`, `sub`, `iss`, `aud`, `exp`, `auth_time`, `nonce` y atributos mínimos. | Sirve para crear o actualizar la identidad de aplicación; no es un permiso. |
| Refresh token | Credencial opaca de Cognito para obtener nuevos tokens. | Se almacena cifrada en sesión server-side, con rotación/revocación y TTL; nunca en el navegador. |

### 4.5 JWKS, expiración, rotación y revocación

- El BFF obtiene la clave pública desde el JWKS del issuer configurado, cachea por `kid` y actualiza ante una clave desconocida dentro de límites de tiempo y tasa.
- Se acepta solo el algoritmo aprobado (por defecto `RS256` si Cognito lo emite), se valida firma, issuer exacto, audiencia/client_id correspondiente, `exp`, `nbf`/`iat` cuando aplique y `token_use`.
- La rotación de claves de Cognito no debe interrumpir sesiones válidas: el cache JWKS debe tolerar claves activas anteriores durante su ventana de expiración y fallar cerradamente ante una firma no verificable.
- La expiración exacta es una decisión de configuración. Como punto de partida de seguridad, se recomienda access token de corta duración, sesión BFF con idle timeout y máximo absoluto, y refresh token con vida limitada; los valores concretos deben aprobarse con MFA, usabilidad y costos.
- La revocación debe invalidar la sesión BFF y, cuando sea compatible, el refresh token mediante el mecanismo de Cognito. Un access token ya emitido puede seguir siendo válido hasta su `exp`; por ello debe ser de corta duración y el backend debe consultar el estado/versión de sesión cuando la política exija revocación inmediata.
- Errores de token se clasifican como `invalid_token`, `expired_token`, `inactive_session`, `revoked_session` o `issuer_mismatch`; las respuestas públicas no revelan la causa criptográfica detallada.

### 5.3 Algoritmo de decisión

Para cada petición protegida, Lambda debe ejecutar una decisión determinista equivalente a:

1. Obtener la sesión segura desde la cookie o el JWT desde la frontera autorizada.
2. Validar la credencial y la sesión; si falta o está vencida, devolver 401.
3. Resolver `cognitoSub` a `ApplicationUser` y comprobar estado activo.
4. Resolver gimnasio y contexto del recurso; rechazar un `gymId` enviado por el navegador si no coincide con la relación verificada.
5. Consultar la capacidad efectiva y su alcance para el rol y contexto actuales.
6. Comprobar relación de recurso: propio, asignado, del gimnasio o público aprobado.
7. Aplicar reglas de negocio y estado del recurso: publicación, fecha, cupo, membresía, ventana horaria y versión.
8. Registrar una auditoría mínima y devolver la proyección autorizada; nunca devolver el objeto completo cuando basten campos mínimos.
9. Si falta capacidad, devolver 403; si el recurso no existe o no pertenece al contexto autorizado, aplicar 404 consistente para evitar enumeración.

Una decisión frontend puede ocultar una acción, pero la decisión backend es la única que autoriza la operación.

### 5.4 Estados de acceso y errores

| Estado | Condición | Comportamiento |
|---|---|---|
| `unauthenticated` | No hay sesión válida | Redirigir al flujo Cognito mediante BFF; no mostrar datos. |
| `authenticated` | Sesión y usuario activo verificados | Cargar shell y capacidades efectivas. |
| `denied` | Identidad válida sin capacidad o fuera de alcance | Mostrar acceso denegado; no filtrar el recurso. |
| `expired` | Sesión o token vencido | Interrumpir operación; intentar recuperación controlada o cerrar sesión. |
| `revoked` | Sesión/refresh revocado | Invalidar estado local y exigir nueva autenticación. |
| `unavailable` | Portal aún no habilitado | Mantener pantalla informativa actual; no registrar rutas operativas. |

El frontend no debe convertir un 404 público en una pantalla que revele si un recurso privado existe. La política de 403/404 se definirá por endpoint y se probará contra enumeración.

| Acceso denegado | `AuthorizationDecision` con `allowed: false` y motivo `missing-capability`, `out-of-scope` o `inactive-user` | El backend devuelve 403 cuando la identidad existe pero la capacidad o el alcance no están concedidos. |
| Sesión expirada | `SessionStatusContract.status = 'expired'` y `AuthErrorContract.code = 'SESSION_EXPIRED'` | El frontend interrumpe la operación y aplica recuperación controlada o cierre de sesión; no confía en el reloj local. |

Los valores como `application-user-id`, `gym-id-verificado`, `request-id-opaco` y `wod-id-publico` usados en ejemplos JSON son marcadores conceptuales no operativos. No son dominios, identificadores AWS, credenciales ni datos reales.

## 6. Contratos backend conceptuales

Estos endpoints no existen en el backend actual. Sus rutas son propuestas sujetas a revisión de la superficie API existente y no deben implementarse en este incremento.

### 6.1 Convenciones comunes

- Todas las rutas privadas requieren HTTPS en producción y una sesión BFF válida; un JWT directo solo se aceptará en una frontera explícitamente aprobada para clientes no browser.
- El navegador no envía roles, capacidades, `gymId` efectivo ni tokens como parámetros de autorización. Los identificadores de recurso pueden viajar en path/query, pero se verifican contra la sesión y la base de datos.
- Las respuestas usan JSON UTF-8, un `requestId` opaco y un envelope de error estable. Los mensajes públicos no incluyen JWT, cookies, stack traces, emails, nombres de tablas ni detalles criptográficos.
- Las operaciones de lectura no reciben ni procesan `Idempotency-Key`; esa convención queda reservada a escrituras futuras.
- Las respuestas privadas no se almacenan en CloudFront ni en cachés compartidas. La política de caché de cada endpoint se indica abajo.
- La auditoría registra `requestId`, `sub` o identificador pseudónimo, acción, tipo/id de recurso, decisión, `gymId` verificado, política/versión y marca de tiempo. No registra tokens, cookies, códigos OAuth, refresh tokens, emails ni cuerpos completos.

```ts
export interface ApiErrorEnvelope {
  readonly error: {
    readonly code: string;
    readonly message: string;
    readonly requestId: string;
    readonly retryable?: boolean;
  };
}

export interface ApiMeta {
  readonly requestId: string;
  readonly policyVersion: string;
}
```

### 6.2 `GET /me`

**Propósito.** Devolver la identidad mínima de la sesión y el estado de autenticación para inicializar el shell privado. No es un perfil completo ni una fuente de permisos crudos.

**Identidad y capacidad.** Requiere sesión BFF válida y usuario de aplicación activo. Capacidad: `profile:read`. Alcance: `own`. El backend deriva el usuario desde la sesión; ignora cualquier rol o `gymId` enviado por el cliente.

**Respuesta 200 propuesta.**

```json
{
  "data": {
    "user": {
      "id": "application-user-id",
      "displayName": "Nombre mínimo aprobado",
      "roles": ["STUDENT"],
      "gymId": "gym-id-verificado"
    },
    "session": {
      "status": "authenticated",
      "expiresAt": "2026-10-31T12:00:00-04:00"
    }
  },
  "meta": {
    "requestId": "request-id-opaco",
    "policyVersion": "authz-v1"
  }
}
```

El `displayName`, el email y cualquier dato personal son opcionales y solo se proyectan si hay una finalidad aprobada. `roles` y `gymId` son proyecciones de la base de aplicación, no claims confiados directamente desde el navegador.

**Errores.**

- `401 AUTH_REQUIRED` o `SESSION_EXPIRED`: no hay sesión válida; frontend redirige al login BFF.
- `403 USER_INACTIVE` o `IDENTITY_NOT_PROVISIONED`: la identidad existe pero está suspendida, desactivada o sin provisioning; no se revelan datos.
- `404 USER_NOT_FOUND`: un `sub` válido no tiene una identidad de aplicación mapeada, cuando la política decida no crearla automáticamente.
- `503 IDENTITY_STORE_UNAVAILABLE`: dependencia temporalmente indisponible; no reintentar en bucle sin backoff.

**Seguridad y datos mínimos.** Validar sesión, estado activo, relación de gimnasio y versión de revocación. No devolver tokens, email, teléfono, membresía, pagos, reservas ni claims completos.

**Caché.** `Cache-Control: no-store`; `Pragma: no-cache` cuando el cliente lo requiera. No usar caché compartido.

**Auditoría.** Evento `me.read` con resultado autorizado/denegado, `sub` pseudónimo, `gymId` verificado y `requestId`; no registrar la respuesta completa.

### 6.3 `GET /me/capabilities`

**Propósito.** Entregar las capacidades efectivas y sus alcances para la sesión actual, después de consultar la base de aplicación. Permite que Angular adapte la navegación sin convertir el resultado en una barrera de seguridad.

**Identidad y capacidad.** Requiere sesión válida, usuario activo y `profile:read` en alcance `own`. La capacidad de la propia consulta puede considerarse parte del contrato de bootstrap; no se concede por un claim del navegador.

**Respuesta 200 propuesta.**

```json
{
  "data": {
    "userId": "application-user-id",
    "gymId": "gym-id-verificado",
    "capabilities": [
      {
        "name": "reservations:read",
        "scope": "own"
      },
      {
        "name": "wod:read",
        "scope": "own"
      }
    ],
    "asOf": "2026-10-31T12:00:00-04:00"
  },
  "meta": {
    "requestId": "request-id-opaco",
    "policyVersion": "capabilities-v1"
  }
}
```

La lista se recalcula o se invalida cuando cambian rol, estado, membresía, asignaciones o versión de política. Un valor ausente significa “no concedida”; el cliente no debe inferir capacidades por omisión.

**Errores.** 401 para sesión ausente/vencida; 403 para usuario inactivo o sin `profile:read`; 404 si no existe identidad de aplicación; 503 si el almacén de políticas o usuarios no está disponible.

**Seguridad y datos mínimos.** No devolver la matriz completa de otros roles, reglas internas, identificadores de recursos no autorizados ni tokens. La respuesta puede incluir solo capacidades efectivas del usuario y su contexto autorizado.

**Caché.** Preferir `no-store` en el primer flujo. Si más adelante se usa caché privado, debe ser de vida muy corta, invalidarse por versión de política/usuario y nunca compartirse entre sesiones.

**Auditoría.** Evento `capabilities.read` con decisión, versión de política y número de capacidades, sin listar datos sensibles ni registrar el cuerpo completo.

### 6.4 Primer endpoint privado de solo lectura: `GET /me/wod/daily`

**Propósito.** Probar el primer flujo vertical privado con una lectura de bajo riesgo: WOD publicado y visible para la fecha de negocio. No expone datos personales, financieros, reservas ni operaciones de escritura. La ruta es una propuesta sujeta a revisión de endpoints existentes.

**Identidad y capacidad.** Requiere sesión BFF válida, usuario activo y `wod:read`. Alcance:
- `STUDENT`: `own` en el sentido de contenido permitido para su gimnasio/membresía autorizada; no se devuelve información de otros alumnos.
- `COACH`: `assigned`, limitado a clases/WOD asignados cuando el contenido esté asociado a una clase.
- `ADMIN`: `gym`, dentro del gimnasio autorizado.
- `COMMUNITY_MANAGER`: no tiene `wod:read` según la matriz aprobada.

**Entrada.** Query `date=YYYY-MM-DD` opcional; si se omite, Lambda calcula la fecha de negocio en `America/Asuncion`. El navegador no controla la zona horaria de decisión. Se rechazan fechas fuera de la ventana autorizada y valores mal formados con 400, sin revelar reglas internas.

**Respuesta 200 propuesta.**

```json
{
  "data": {
    "date": "2026-10-31",
    "timezone": "America/Asuncion",
    "wod": {
      "id": "wod-id-publico",
      "title": "WOD publicado",
      "description": "Contenido aprobado y visible",
      "visibleAt": "2026-10-31T00:00:00-04:00"
    }
  },
  "meta": {
    "requestId": "request-id-opaco",
    "policyVersion": "wod-v1"
  }
}
```

La respuesta puede ser `{ "data": { "wod": null } }` cuando no exista contenido publicado para la fecha, según la política de producto; esa ausencia no debe revelar si un WOD futuro existe.

**Errores.**

- `400 INVALID_DATE`: fecha mal formada o fuera de la ventana permitida.
- `401 AUTH_REQUIRED` / `SESSION_EXPIRED`: sesión ausente o vencida.
- `403 FORBIDDEN` / `MISSING_CAPABILITY`: identidad válida sin `wod:read` o fuera de alcance.
- `404 WOD_NOT_FOUND`: solo cuando la política permita distinguir ausencia pública; si existe riesgo de enumeración, se usa una respuesta de ausencia no distinguible.
- `503 CONTENT_STORE_UNAVAILABLE`: almacén indisponible; no se sirve contenido no verificado.

**Seguridad y datos mínimos.** Lambda verifica estado de publicación, fecha de visibilidad, gimnasio/membresía, asignación del coach y versión del contenido. No devuelve autores, comentarios, alumnos, reservas, pagos, ubicaciones sensibles ni metadatos internos.

**Caché.** Para el primer flujo, `Cache-Control: private, max-age=60` como máximo y solo si se puede garantizar que la respuesta no contiene datos de otro usuario; de lo contrario, `no-store`. Nunca caché pública/CDN para respuestas asociadas a una sesión. La invalidación debe considerar fecha, gimnasio, estado de publicación y versión.

**Auditoría.** Evento `wod.daily.read` con resultado, fecha de negocio, gym verificado, rol/capacidad y `requestId`; no registrar descripción completa si se considera contenido sensible ni identificar alumnos.

## 7. Protección backend

### 7.1 Validación JWT y de sesión

Para un JWT recibido en una frontera autorizada, el validador debe comprobar, como mínimo:

1. firma contra JWKS y algoritmo permitido;
2. issuer exacto del User Pool aprobado;
3. audience/client_id esperado según el tipo de token y el flujo;
4. `exp`, `nbf` e `iat` con tolerancia de reloj pequeña y justificada;
5. `token_use` (`access` o `id`) compatible con el endpoint;
6. `sub` presente y estable;
7. scopes solicitados cuando el endpoint use scopes OAuth;
8. estado de sesión/revocación y versión de identidad en la aplicación;
9. relación usuario/recurso, capacidad y alcance;
10. estado activo del usuario y reglas de negocio.

Un access token válido no implica automáticamente `ADMIN`, acceso a pagos ni permiso sobre un recurso. Un ID token no debe usarse como bearer token de API. Un grupo de Cognito es una señal de provisioning, no una autorización definitiva.

### 7.2 Qué puede hacer API Gateway HTTP API

API Gateway puede y debe aplicar controles de borde:

- TLS/HTTPS y eliminación de headers inseguros;
- CORS con orígenes exactos, métodos, headers y credenciales explícitas; no `*` para cookies;
- límites de tamaño, throttling/cuotas y protección básica contra abuso;
- rutas/métodos permitidos y respuestas de error normalizadas;
- autorizador JWT para clientes directos aprobados, validando firma, issuer, audiencia, expiración y scopes;
- logs de acceso con campos limitados y enmascarados;
- validación básica de esquema cuando la integración la soporte.

API Gateway no debe considerarse suficiente para:

- resolver una cookie de sesión BFF y su estado de revocación;
- comprobar si el usuario está activo en la base de aplicación;
- calcular capacidades dinámicas, membresías, asignaciones o estado de recurso;
- comprobar relación `own`/`assigned`/`gym`/`approved-public`;
- aplicar reglas de reserva, WOD, pagos, idempotencia o transacciones;
- decidir si un 403 debe ocultarse como 404 para evitar enumeración;
- auditar el resultado de negocio con contexto completo.

Esas decisiones corresponden a Lambda o a un authorizer Lambda especializado, y Lambda conserva la validación final aunque API Gateway haya aceptado el JWT.

### 7.3 Controles Lambda obligatorios

- parsear solo headers/query/path esperados y rechazar entradas desconocidas o excesivas;
- resolver la sesión por cookie opaca y rotarla cuando corresponda;
- comprobar CSRF para métodos inseguros mediante token y validación de `Origin`/`Referer`;
- consultar usuario, gimnasio, membresía, asignaciones y estado activo;
- evaluar capacidad y alcance contra el recurso solicitado;
- aplicar reglas de negocio y consistencia;
- usar consultas acotadas, sin scans no justificados;
- aplicar conditional writes/transacciones e idempotencia en escrituras futuras;
- emitir auditoría mínima y `requestId`;
- devolver errores públicos estables y evitar detalles internos.

## 8. Contratos frontend

### 8.1 Principio de reutilización

Angular 22 mantendrá componentes `standalone`, `OnPush`, carga perezosa y modelos tipados. Los tipos de rol y capacidad existentes bajo `frontend/src/app/portal/models/` son la fuente de verdad del cliente:

```ts
import type { PortalRole } from './portal/models/portal-role';
import type {
  PortalCapability,
  CapabilityScope,
  RoleCapabilityDefinition,
} from './portal/models/portal-capability';
```

No se duplicarán los literales de roles/capacidades en servicios de auth ni guards. El frontend no importará código backend ni tratará una respuesta de `/me/capabilities` como autorización definitiva.

### 8.2 Interfaces conceptuales

### 8.3 Rutas protegidas futuras

Las rutas siguientes son diseño, no están registradas ni operativas en el HEAD actual:

```text
/portal/app
/portal/app/dashboard
/portal/app/admin/...
/portal/app/coach/...
/portal/app/student/...
/portal/app/community/...
/portal/app/access-denied
/portal/app/session-expired
```

Cada ruta llevará metadatos de capacidades requeridas para UX. Un guard futuro podrá:

- esperar el estado inicial `loading`;
- redirigir a `/portal/login` o al endpoint BFF de login si está sin sesión;
- mostrar `AccessDeniedComponent` ante 403;
- mostrar `SessionExpiredComponent` ante expiración/revocación;
- preservar la ruta relativa autorizada como retorno validado.

El guard nunca leerá un rol de una cookie, parámetro de ruta, `localStorage` o claim sin validar. La autorización definitiva seguirá en Lambda.

### 8.4 Recuperación de sesión y concurrencia

- Al iniciar Angular, una única operación de bootstrap consulta `/me`; no se lanzan renovaciones desde cada componente.
- Si varias peticiones reciben 401, una sola coordenada de renovación evita condiciones de carrera.
- Si la renovación falla por expiración o revocación, se cancelan peticiones pendientes, se limpia el estado sensible y se muestra sesión expirada.
- Los reintentos usan backoff limitado y no reintentan escrituras sin una clave de idempotencia; en este incremento no hay escrituras.
- El reloj del cliente no decide expiración definitiva; el backend y los headers de sesión son la fuente de verdad.

### 8.5 Logout

El logout futuro será una petición segura al BFF, no una simple limpieza visual:

1. Angular cancela operaciones en curso y bloquea acciones duplicadas.
2. El BFF invalida la sesión server-side y revoca el refresh token cuando corresponda.
3. La cookie se elimina con el mismo nombre, dominio, ruta y atributos con los que se creó.
4. El BFF redirige al logout de Cognito con un post-logout URI aprobado.
5. Angular limpia `AuthState`, capacidades, retornos y estado de menús; no guarda tokens ni roles.
6. La navegación posterior vuelve a una ruta pública o a la pantalla de login, sin datos privados en caché visible.

### 8.6 Compatibilidad de foco

El shell público usa `#contenido-principal`; el shell privado usa `#portal-contenido-principal`. No se modificará `NavigationFocusService` en este documento. El diseño futuro deberá resolver la diferencia mediante una frontera común:

1. cada shell expone un selector de contenido principal mediante metadata o atributo estable;
2. el servicio de foco consulta el shell activo o un registro de targets;
3. el público conserva `#contenido-principal` y el privado `#portal-contenido-principal`;
4. después de cada `NavigationEnd`, se espera la renderización y se enfoca el target con `preventScroll` cuando corresponda;
5. al cerrar el menú móvil se restaura el foco al disparador; al navegar se prioriza el contenido principal;
6. si el target no existe, no se produce una excepción ni se enfoca un elemento incorrecto.

Esta decisión evita cambiar el servicio público actual y permite añadir el selector privado en una fase autorizada.

## 9. Reglas de negocio que deben conservarse

Estas reglas no se implementan en NP-003.7C.1 y deberán ser verificadas por Lambda antes de cualquier operación futura:

| Regla | Responsable y contrato |
|---|---|
| Altas de alumnos solamente por `ADMIN` | `students:create`; rechazar cualquier otro rol, incluso con claim aparente. |
| Una reserva por alumno y día | Fecha de negocio calculada en `America/Asuncion`; restricción atómica mediante clave/conditional write. |
| Cancelación hasta una hora antes | Lambda calcula la ventana con hora de inicio y política aprobada; el navegador no decide. |
| WOD visible según fecha autorizada | Verificar estado publicado, fecha de visibilidad, gimnasio y alcance. |
| Membresías y paquetes | Consultar estado y vigencia; no asumir una única modalidad. |
| Pagos en PYG enteros | Transmitir y calcular importes como enteros; nunca `float`. |
| Idempotencia | Escrituras críticas requieren clave idempotente, registro de resultado y replay seguro. |
| Autorización por recurso | Comprobar `sub`, `gymId`, `classId`, `reservationId`, asignación y alcance. |
| Transacciones y escrituras condicionales | Usar transacciones DynamoDB o conditional writes para invariantes y concurrencia. |

El primer endpoint WOD de este documento es solo lectura y no habilita ninguna de las operaciones anteriores.

## 10. Seguridad y privacidad

### 10.1 Clasificación de riesgos

| Riesgo | Estado | Mitigación requerida |
|---|---|---|
| XSS roba tokens | Mitigado parcialmente por BFF | Tokens fuera del navegador; CSP estricta, escaping Angular, sanitización de contenido, Trusted Types cuando sea viable y revisión de dependencias. |
| XSS ejecuta acciones con cookie | Pendiente | CSP, SameSite, token CSRF para métodos inseguros, límites de sesión y monitoreo. |
| CSRF | Pendiente de diseño final | Cookie `Secure`, `HttpOnly`, `SameSite` adecuado; validar `Origin`/`Referer`; token CSRF por sesión para POST/PUT/PATCH/DELETE. |
| IDOR/BOLA | Pendiente | Lambda verifica identidad, gym, clase, reserva y relación de recurso; 404/403 consistentes y pruebas cruzadas. |
| CORS abierto | Decisión tomada, implementación pendiente | Reemplazar `*` por orígenes exactos; credenciales explícitas; preflight restringido; pruebas de origen no autorizado. |
| Tokens en navegador | Mitigado por BFF | No access/ID/refresh tokens en Angular, `localStorage`, sessionStorage, URL o logs. |
| Cookie robada/replay | Pendiente | Cookie `__Host-` cuando el dominio lo permita, Secure/HttpOnly/SameSite, rotación de ID, TTL corto, revocación y detección de anomalías. |
| Claims obsoletos | Pendiente | Session version/revocation check; access token corto; consulta de estado activo y capacidades actuales. |
| MFA débil o SMS | Decisión abierta | No habilitar SMS automáticamente; evaluar TOTP/WebAuthn según Cognito y perfil de riesgo; recuperación solo por correo hasta aprobar otro canal. |
| Recuperación de cuenta | Pendiente | Email only como baseline, rate limiting, códigos efímeros, notificación de cambios y revisión de enumeración de usuarios. |
| Ataques de intentos | Pendiente | Límites por IP/cuenta, bloqueo progresivo, monitoreo y respuesta sin revelar existencia. |
| Privacidad de alumnos | Pendiente | Mínimo privilegio, proyecciones mínimas, cifrado, retención definida y aviso/consentimiento pendiente. |
| Datos personales en logs | Pendiente | No registrar tokens, cookies, emails, cuerpos completos ni IDs sin necesidad; enmascarar y limitar retención. |
| Sesiones concurrentes | Decisión abierta | Definir máximo de sesiones por usuario/dispositivo, revocación individual/global y comportamiento en login nuevo. |
| Dependencias | Pendiente | Biblioteca OIDC/BFF aprobada, lockfile, inventario/SBOM, análisis de vulnerabilidades y actualizaciones controladas. |
| Abuso de endpoints | Pendiente | Throttling, cuotas, paginación, límites de query, timeouts, alarmas y posible WAF solo si se aprueba por costo/riesgo. |

### 10.2 CSP y contenido

La CSP futura deberá ser compatible con Angular, CloudFront/S3 y los orígenes estrictamente necesarios. Se recomienda comenzar con una política restrictiva que:

- deshabilite `unsafe-eval` salvo justificación técnica;
- limite `script-src`, `style-src`, `connect-src`, `img-src` y `font-src` a orígenes aprobados;
- use nonces o hashes para scripts inline si fueran inevitables;
- bloquee framed content no autorizado;
- se pruebe en modo de reporte antes de aplicar bloqueo total;
- no dependa de contenido remoto no revisado para el portal privado.

La sanitización de contenido WOD, galerías y actividades debe asumir que el texto puede ser hostil. Angular escapa plantillas por defecto, pero eso no sustituye validación backend, políticas de tipos MIME ni revisión de archivos subidos.

### 10.3 Privacidad y auditoría

- Recopilar solo datos necesarios para autenticación, autorización, operación aprobada y auditoría.
- Separar identidad Cognito de datos de negocio; usar `sub` como clave de correlación interna, no como identificador público.
- No exponer email, teléfono, dirección, pagos, membresías completas ni historial de otros alumnos en `/me` o respuestas de error.
- Definir retención de logs de seguridad y auditoría; el baseline de una semana es una referencia, no una política legal aprobada.
- Restringir acceso a logs y métricas con IAM de mínimo privilegio.
- Enmascarar IPs cuando no sean necesarias para seguridad y documentar la base legal/consentimiento antes de procesar datos personales.

### 10.4 Controles mínimos antes de producción

1. Revisión humana de seguridad y privacidad.
2. Revisión humana WCAG 2.2 AA y responsive en 320, 768 y 1440 px.
3. Pruebas de CORS, CSRF, XSS, IDOR/BOLA, expiración, revocación y logout.
4. Confirmación de dominio, redirect URIs, correo, contenido oficial y residencia de datos.
5. Presupuesto AWS realista y alertas antes de despliegue.
6. Aprobación explícita de MFA, recuperación, sesiones concurrentes y retención de logs.

- Lambda Node.js 24 bajo demanda, sin provisioned concurrency;
- DynamoDB Standard on-demand con tabla principal, dos GSI sparse, PITR y TTL;
- CloudWatch Logs de retención corta y métricas y alarmas limitadas;
- EventBridge Scheduler para WOD diario;
- SES con IP compartida para correos transaccionales;
- una sola región, con `us-east-1` como referencia del baseline.

### 11.2 Costos incrementales por estrategia

| Componente | SPA + PKCE | BFF + cookies | Comentario presupuestario |
|---|---|---|---|
| Cognito | MAU, mensajes y funciones de identidad utilizadas. | Igual, más posibles flujos de recuperación/logout según uso. | No habilitar SMS ni MFA por SMS sin aprobación; el costo depende de MAU y canales. |
| API Gateway HTTP API | Requests, data processing y posibles authorizers. | Requests de bootstrap, callback, logout, refresh y APIs; posible mayor tráfico de sesión. | Medir requests por usuario y tamaño de respuesta; evitar logs excesivos. |
| Lambda | Ejecuciones de API y authorizer si se usa. | Ejecuciones adicionales del BFF para sesión, token exchange, renovación, logout y auditoría. | BFF puede aumentar duración/invocaciones; usar memoria/tiempo mínimos medidos. |
| DynamoDB | Lecturas/escrituras de dominio. | Lecturas/escrituras adicionales de sesión, revocación y tal vez tabla de sesiones. | Una tabla/índice adicional puede ser viable, pero debe incluirse en el presupuesto. |
| CloudWatch | Logs/métricas de API/Lambda. | Más eventos de sesión, CSRF, logout y auditoría. | Retención corta, muestreo/estructuración y alarmas acotadas; no registrar datos personales. |
| S3/CloudFront | Frontend y transferencia pública/privada. | Igual; el BFF no cambia necesariamente el hosting estático. | Medir requests/GB y precio de transferencia de la región elegida. |
| SES/correo | Correos de recuperación/notificaciones. | Igual, posiblemente más eventos de seguridad. | No activar canales premium; confirmar identidad, volumen y tarifas. |
| EventBridge Scheduler | WOD diario. | Igual. | Costo fijo/invocación pequeño pero no debe omitirse. |
| WAF/otros | Opcional y no incluido. | Opcional y no incluido. | WAF, NAT, VPC, IP dedicada, multi-Región o provisioned concurrency requieren nueva aprobación. |

### 11.3 Supuestos de consumo que faltan

Para producir un presupuesto realista se necesitan, como mínimo:

1. usuarios activos mensuales (MAU) y proporción que usa el portal privado;
2. logins, refresh, logout y recuperaciones por usuario/mes;
3. solicitudes API por usuario/mes y tamaño medio de respuesta;
4. duración p95/p99 y memoria de cada Lambda;
5. lecturas/escrituras DynamoDB por flujo, tamaño de ítems, GSI y PITR;
6. volumen de logs en GB/mes y retención aprobada;
7. solicitudes y transferencia CloudFront/S3;
8. correos SES/mes y canal de recuperación;
9. eventos EventBridge y alarmas/métricas;
10. región, impuestos, soporte y posibles cargos de transferencia saliente;
11. número de sesiones concurrentes y vida máxima de sesión;
12. necesidad de WAF, MFA avanzado, SMS, correos verificados adicionales o residencia específica.

### 11.4 Impacto relativo y recomendación económica

SPA/PKCE puede tener menos lecturas de sesión y menos código server-side, pero desplaza más responsabilidad al cliente y puede requerir más llamadas de renovación o authorizer. BFF añade invocaciones Lambda, lecturas/escrituras de sesión y logs, pero centraliza renovación, revocación y autorización, y puede reducir errores operativos y exposición de tokens.

La recomendación BFF se acepta económicamente solo si el modelo de consumo medido mantiene el total bajo US$ 20/mes y el objetivo interno bajo US$ 15/mes. Antes de implementar se debe:

- instrumentar un modelo de tráfico conservador;
- simular el peor caso razonable de MAU y requests;
- comparar BFF con SPA usando los mismos supuestos;
- definir alertas de presupuesto en 50 %, 75 %, 90 % y 100 %;
- revisar Cost Explorer/anomalías y etiquetar recursos con proyecto, fase y ambiente;
- rechazar servicios fijos o premium que no quepan en el presupuesto sin autorización.

## 12. Criterios de aceptación futuros

Estos criterios corresponden a NP-003.7C.2 o incrementos posteriores. No se simulará autenticación operativa en este incremento documental.

### 12.1 Identidad y sesión

- [ ] Usuario sin sesión que solicita `/portal/app`: no ve datos privados y es dirigido al flujo de login aprobado.
- [ ] Callback con `state` válido, `nonce` válido y PKCE correcto crea una sesión opaca.
- [ ] Callback con `state` ausente, incorrecto o reutilizado falla cerradamente y no crea sesión.
- [ ] Callback con `code_verifier` ausente o incorrecto falla y no entrega tokens al navegador.
- [ ] Token firmado por un issuer no aprobado es rechazado.
- [ ] Token con audiencia/client_id incorrecto es rechazado.
- [ ] Token con `token_use` incorrecto para el endpoint es rechazado.
- [ ] Token vencido produce 401/estado expirado y no se renueva indefinidamente.
- [ ] Token inválido o con firma incorrecta produce 401 sin revelar detalles criptográficos.
- [ ] Usuario de Cognito sin identidad de aplicación recibe el comportamiento aprobado (403/404 controlado).
- [ ] Usuario suspendido o desactivado no accede aunque su JWT siga vigente.
- [ ] Sesión revocada invalida cookie, refresh y estado frontend.
- [ ] Logout elimina cookie, revoca sesión y redirige correctamente; el botón atrás no restaura datos privados.
- [ ] Sesión expirada durante varias peticiones produce una única transición de estado y no bucles de login.

### 12.2 Autorización y recursos

- [ ] Identidad válida sin capacidad obtiene 403 y pantalla de acceso denegado.
- [ ] `ADMIN` puede acceder a recursos del gimnasio autorizado, pero no a otro gimnasio.
- [ ] `COACH` accede a clases, alumnos, reservas, asistencia y WOD asignados.
- [ ] Profesor accediendo a recursos no asignados recibe 403/404 consistente y no obtiene datos.
- [ ] `STUDENT` accede solo a reservas, membresía, WOD y perfil propios.
- [ ] Un alumno intenta leer datos de otro alumno: no obtiene datos y se registra intento.
- [ ] `COMMUNITY_MANAGER` accede solo a contenido/galería/actividades públicos aprobados.
- [ ] Community Manager intentando acceder a pagos recibe 403 y no ve información financiera.
- [ ] Un `gymId` enviado por el navegador no puede ampliar el alcance verificado por Lambda.
- [ ] Un rol enviado por el navegador no puede escalar privilegios.
- [ ] Claims obsoletos después de un cambio de rol o suspensión producen la decisión actualizada.
- [ ] Las respuestas 401 y 403 usan envelope estable, `requestId` y mensajes no sensibles.
- [ ] La política 403/404 evita enumeración de recursos privados.

### 12.3 Primer flujo vertical y reglas de negocio

- [ ] `GET /me` devuelve solo datos mínimos y no tokens/claims crudos.
- [ ] `GET /me/capabilities` devuelve capacidades efectivas y alcances, sin matriz de otros roles.
- [ ] `GET /me/wod/daily` requiere sesión y `wod:read`.
- [ ] WOD futuro/no publicado no se devuelve a un alumno.
- [ ] La fecha de negocio se calcula en `America/Asuncion`, no con la zona del navegador.
- [ ] La respuesta WOD no incluye datos personales, financieros, reservas ni metadatos internos.
- [ ] La caché privada no filtra datos entre usuarios ni gimnasios.
- [ ] Escrituras futuras conservan idempotencia, transacciones y conditional writes antes de exponerse.

### 12.4 Frontend, navegación y accesibilidad

- [ ] Carga inicial muestra estado de carga seguro y no contenido privado por defecto.
- [ ] Rutas privadas protegidas no renderizan componentes operativos sin sesión válida.
- [ ] 401 redirige o recupera sesión según política; 403 muestra acceso denegado.
- [ ] Sesión expirada muestra `SessionExpiredComponent` y ofrece retorno seguro.
- [ ] Logout limpia estado, capacidades y menús.
- [ ] La navegación móvil conserva foco, `Escape`, `Tab` y `Shift+Tab`.
- [ ] En el shell público el foco posterior a navegación llega a `#contenido-principal`.
- [ ] En el shell privado el foco posterior a navegación llega a `#portal-contenido-principal`.
- [ ] La resolución de foco no lanza errores cuando el target no existe.
- [ ] Revisión visual en 320, 768 y 1440 px.
- [ ] Auditoría humana WCAG 2.2 AA, contraste, foco visible, orden de teclado y reducción de movimiento.

### 12.5 Red, abuso y observabilidad

- [ ] CORS acepta solo orígenes aprobados y rechaza un origen no autorizado.
- [ ] Las solicitudes credenciales no usan CORS wildcard.
- [ ] Métodos inseguros requieren CSRF válido y origen consistente.
- [ ] Throttling/cuotas limitan abuso sin bloquear el flujo legítimo esperado.
- [ ] Logs no contienen tokens, cookies, códigos OAuth, refresh tokens, emails ni cuerpos completos.
- [ ] Auditoría incluye `requestId`, decisión, recurso, gym verificado y versión de política.
- [ ] Alarmas de errores 4xx/5xx, latencia, throttling y presupuesto están configuradas.
- [ ] Rotación JWKS con `kid` nuevo y viejo se prueba sin interrumpir sesiones válidas.
- [ ] Revocación de refresh/session se prueba con access token aún vigente y se documenta su ventana residual.
